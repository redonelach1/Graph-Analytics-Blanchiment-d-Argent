# Dataset Specifications and Integration Plan

Companion to the Mini-Projet 17 implementation plan and technical specifications.

Research date: 1 November 2026. Dataset documentation was reviewed online; archives were not downloaded or profiled. Counts below are approximate publisher figures unless otherwise specified. Availability, exact schema, record counts, licenses, and checksums must be confirmed during acquisition.

## 1. Dataset selection decision

Use three complementary sources:

1. Controlled generated fixtures for exact temporal-triangle acceptance tests.
2. IBM AMLSim example graphs for small-to-large graph integration and performance tests.
3. IBM Transactions for Anti Money Laundering (AML), starting with HI-Small and then LI-Small, for richer synthetic financial replay.

AMLSim and the IBM virtual-world AML dataset are distinct generators/dataset families. Do not label the newer IBM virtual-world data as having been generated by AMLSim simply because it includes AMLSim-inspired pattern annotations.

No dataset is evidence that a three-account cycle proves laundering.

## 2. Dataset catalog

### DS-01: IBM Transactions for Anti Money Laundering — HI-Small

Primary download/catalog:
https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml/data

Publisher reference:
https://github.com/IBM/AML-Data

Files to obtain first:
- HI-Small_Trans.csv
- HI-Small_Patterns.txt
- Account metadata file, if included in the selected release; inspect its schema before use.

Publisher overview: approximately 5 million transactions and 515,000 bank accounts. HI means a relatively higher illicit ratio, not a balanced fraud dataset. The overview lists approximately 5,100 laundering transactions. Treat these as rounded figures and profile the actual release.

Nature: synthetic multi-agent virtual-world financial transfers with transaction laundering labels and supplementary pattern descriptions. It is not anonymized real bank-customer data.

License: Community Data License Agreement — Sharing 1.0. The repository code license is separate; the repository's Apache 2.0 license does not replace the data license.

Acquisition: use the publisher-linked Kaggle listing. Login/authentication may be needed; confirm in the actual download workflow. Do not download the entire collection by default.

Project use:
- Adapt financial CSV records to the Kafka input contract.
- Exercise multi-bank account identities and currencies.
- Replay continuous chronological sections through Spark.
- Evaluate alert behavior and supporting evidence on a richer transaction network.
- Inspect available pattern annotations for candidate cycles.

Limitations:
- Laundering labels do not mean “three-account cycle within ten minutes.”
- Pattern files describe selected patterns, not every laundering transaction.
- Ten-minute triangle positives may be sparse or absent; profile rather than assume.
- Publisher notes activity outside the primary date range; inspect temporal tails before evaluation.

### DS-02: IBM Transactions for Anti Money Laundering — LI-Small

Same official dataset catalog as DS-01.

Required files:
- LI-Small_Trans.csv
- LI-Small_Patterns.txt

Publisher overview: approximately 7 million transactions, 705,000 accounts and 4,000 laundering transactions. LI has a relatively lower illicit ratio.

License: CDLA-Sharing-1.0.

Project use:
- Test behavior in a lower-illicit-prevalence environment.
- Compare alerts per million transactions with HI-Small.
- Run a second independent replay workload.

Important: HI-Small and LI-Small are independently generated datasets; LI-Small is not a filtered HI-Small subset. Do not claim that differing alert rates isolate the effect of illicit prevalence alone.

## 3. Acquisition and provenance specification

Every external dataset MUST have a manifest:

```yaml
dataset_id: ibm-aml-hi-small
source_url: https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml/data
release_identifier: TO_RECORD
retrieved_at: TO_RECORD
license: CDLA-Sharing-1.0
files:
  - filename: HI-Small_Trans.csv
    sha256: TO_COMPUTE
    bytes: TO_MEASURE
    rows: TO_PROFILE
raw_schema: TO_RECORD
timestamp_timezone: TO_VERIFY
timestamp_resolution: TO_PROFILE
transformations: []
```

Keep downloaded archives immutable. Do not commit bulk datasets or credentials to Git. Add dataset directories to .gitignore. Retain licensing/attribution files and review redistribution obligations before sharing derived artifacts.

A dataset acquisition task passes only when files are accessible, hashes are recorded, schema inspection succeeds, and applicable terms are documented. Documentation-level discovery is not a verified download.

## 4. Profiling requirements

Before replay, generate a profile report containing:

- Exact row and distinct-account counts.
- Timestamp range, resolution, timezone assumptions, and temporal tails.
- Missing/invalid identifiers and amounts.
- Currency counts and cross-currency transfers.
- Payment-format values and frequency.
- Duplicate rows and duplicate business identifiers, where available.
- Degree distribution and highest-degree accounts.
- Laundering-label prevalence, separately from rule eligibility.
- Known pattern types and cycle lengths where annotations support them.
- Estimated ten-minute active edge/vertex counts.
- Count of three-account candidates on a manageable continuous slice.

The profile MUST state what is measured versus inferred. Do not report published rounded counts as local measurement results.

## 5. Adapter specification

Implement a supporting module such as `dataset_adapter.py`, with separate profiles for IBM AML and AMLSim. It supports the required producer rather than replacing it.

The exact IBM CSV headers MUST be confirmed from the acquired release. Expected concepts commonly include timestamp, sending/receiving bank and account, paid/received amount and currency, payment format, and laundering label. The following is an adapter design, not a claim that headers were verified by downloading the CSV.

| Source concept | Project field | Rule |
|---|---|---|
| Sending bank + account | source_account | Use canonical structured/composite identity |
| Receiving bank + account | target_account | Include bank identity to avoid accidental collisions |
| Timestamp | timestamp | Parse explicit source timezone; convert to UTC |
| Amount paid | montant | Decimal; preserve original values in lineage |
| Payment currency | devise | Preserve source currency |
| Payment format | type_operation | Map through versioned lookup |
| Laundering label | Evaluation-only truth table | Never detector input |
| Pattern annotation | Evaluation-only pattern table | Preserve source reference |

Transaction identity, if the source has no stable ID:

```text
transaction_id = SHA256(dataset release ID + original file identity + original row ordinal)
```

Capture the original ordinal before sorting or filtering. A content-only hash can incorrectly collapse legitimate repeated transfers. Do not use an unstable distributed row identifier for reproducible identity.

Account IDs SHOULD be constructed using a structured encoding or unambiguous escaped format rather than unsafe string concatenation.

AMLSim mapping MUST be based on that archive's schema; do not assume the IBM virtual-world CSV adapter applies unchanged.

## 6. Currency compatibility with the baseline

The baseline specification proposes MAD-only input. External IBM data MUST NOT be relabeled as MAD without conversion.

Choose and approve one approach:

A. Preferred for dataset experiments: permit selected source currencies while requiring all three cycle edges to have the same currency; partition reporting by currency and disable uncalibrated MAD-specific monetary severity thresholds.
B. Filter to a chosen supported source currency and explicitly modify the baseline configuration.
C. For MAD-specific acceptance tests, use the controlled synthetic generator instead.

Do not assume the external dataset contains a useful volume of MAD transactions. Do not treat paid and received amounts in different currencies as directly comparable.

## 7. Timestamp and replay specification

Historical datasets must not be streamed blindly with old business timestamps and interpreted as present-day traffic.

Support these explicit modes:

### Original-time replay

Preserve business timestamps, order by event time, and rate-limit Kafka publication. Use for historical window correctness. Future-skew checks must be configured appropriately; past historical timestamps are not inherently invalid.

### Shifted-time replay

Apply one constant offset to every event timestamp:

```text
new_time = original_time + (replay_start - dataset_start)
```

This preserves time differences and cycle/window durations. Preserve original_time in lineage. If fixed-window alignment changes, record that effect or choose an offset aligned to the slide interval.

### Accelerated delivery

Publish faster while retaining business timestamps. This tests processing capacity without changing the event-time rule.

### Compressed event time

Scale event-time intervals to turn long simulation durations into shorter demonstrations. This CHANGES temporal semantics. Label results as transformed demonstrations and never mix them with original-data effectiveness claims.

Rate limiting controls arrival time; it does not itself change business-event intervals.

For deterministic out-of-order and duplicate experiments, save the scheduling seed and perturbation manifest. A single source-account Kafka key does not guarantee global event-time ordering across partitions.

## 8. Sampling specification

Random row sampling can destroy cycles by removing one of their edges. Use:

- Continuous time sections for event-time and latency evaluation.
- Complete annotated pattern groups for positive-pattern inspection.
- Clearly bounded account neighborhoods for investigation demos.
- Full manageable releases for throughput measurements when feasible.

When a time slice excludes contextual edges, report the truncation. Preserve warm-up/history preceding the measured interval. If tuning rules on labels, use chronological or group-aware splits and avoid splitting one injected/annotated scenario across tuning and final evaluation.

## 9. Ground-truth and metrics specification

Maintain three distinct evaluations:

### E1: Rule correctness

Controlled fixtures encode exact expected temporal triangles, open chains, boundary cases, repeated edges, and late arrivals. These are authoritative for implementation acceptance.

Metrics: expected cycles found, unexpected cycle outputs, evidence correctness and stable alert identity.

### E2: Dataset label association

For external data, report what fraction of alerts contain labeled laundering edges and what fraction of labeled transactions appear in an alert. Declare aggregation: any-edge, all-edge or another stated definition.

Do not call broad laundering coverage the recall of the three-account rule without defining an eligible ground-truth subset. Report how many annotated patterns are actually three-account, same-currency, common-window patterns.

### E3: System performance

Measure input rate, lag, active graph size, candidate motifs, memory/spill, detection duration and end-to-end latency. Dataset laundering labels are unnecessary for throughput measurement.

Do not equate a structurally correct cycle containing legitimate-labeled transfers with a graph-algorithm error. It may be a legitimate cycle and therefore a risk-rule false positive under the chosen labeling interpretation.

## 11. New acceptance tests

| ID | Test | Pass condition |
|---|---|---|
| DS-AT-01 | Repeat adaptation | Identical source rows receive identical transaction IDs |
| DS-AT-02 | Repeated equal-content transfers | Distinct source records remain distinct transactions |
| DS-AT-03 | Same account text at different banks | Distinct canonical account identities |
| DS-AT-04 | Shifted-time replay | Pairwise time differences preserved |
| DS-AT-05 | Accelerated arrival | Original business timestamps unchanged |
| DS-AT-06 | Labels present in source | Labels absent from detector features |
| DS-AT-07 | Currency mapping | No silent currency relabeling or amount comparison across currencies |
| DS-AT-08 | Pattern sampling | Complete selected scenario retained |
| DS-AT-09 | Smallest AMLSim sample | Not assumed to contain injected cycles |
| DS-AT-10 | Original versus compressed time | Separate reports and transformation manifest |

## 12. Recommended execution sequence

1. Controlled 20–100-event fixtures: prove correctness.
2. AMLSim 100 accounts / 10K transactions: prove ingestion and graph construction.
3. AMLSim 1K accounts / 100K transactions: inspect injected patterns and establish a manageable benchmark.
4. HI-Small continuous time slice: validate adaptation, replay, currency policy and annotated-pattern interpretation.
5. Full HI-Small: benchmark only after profiling active graph workload.
6. LI-Small: compare a lower-prevalence independent workload.
7. Medium/large variants: optional scale experiments.
